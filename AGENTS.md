# Project instructions

## Purpose

This repository is an engineer build test for Riverside Council's community hall permit register.

Part 2 implements RC-1, RC-2, and RC-3:

- search the permit register;
- view a permit and renewal history;
- quote and confirm a permit renewal.

RC-4 withdrawal is reserved for Part 4 and must be generated by the agent pipeline, not implemented as part of the manual slice unless explicitly required.

## Source of truth

Use these files in this order:

1. `requirements/stories.md` contains the signed-off stories.
2. `requirements/clarifications.md` contains later business clarifications.
3. `docs/technical-document.md` is the build specification for Part 2.
4. `docs/technical-flowchart.md` explains the request and data flow.
5. `ASSUMPTIONS.md` records conflicts and unresolved decisions when it exists.

Build from the technical document, not directly from the raw requirements. If implementation exposes a gap or contradiction, update the technical document and `ASSUMPTIONS.md` before changing the code.

Never silently alter `requirements/stories.md` or `requirements/clarifications.md`.

## Traceability rules

- Every implemented endpoint, field, status transition, and UI action must have a corresponding technical-document section.
- Do not invent tables, fields, endpoints, statuses, fees, or business rules.
- Do not remove an acceptance criterion because it is inconvenient to implement.
- Keep the fee cap, Council Use exception, 90-day expired-permit rule, newest-first sorting, and payment boundary consistent across documents and code.
- Hall and purpose names shown to officers must come from API data, not duplicated frontend constants.
- If a requirement is unresolved, stop and record the question, owner, and temporary assumption.

## Part 2 implementation

### Backend

- Use Spring Boot REST endpoints described in `docs/technical-document.md`.
- Keep controller, service, and repository responsibilities separate.
- Validate business rules on the server.
- Recalculate and revalidate the renewal during confirmation. Never trust a fee or status sent by the browser.
- Write the renewal record, permit update, and history entry as one transaction.
- Return the documented status codes and error response shape.
- In-memory storage is acceptable, but keep repository interfaces so storage can be replaced.

### Frontend

- Use React for the staff portal.
- Implement loading, populated, empty, validation-error, not-found, and conflict states.
- Preserve search filters when returning from the permit view.
- Show the renewal fee and require confirmation before calling the write endpoint.
- Do not calculate authoritative fees or eligibility in the browser.

### Test data

Seed data must demonstrate:

- an active chargeable permit;
- an active Council Use permit;
- an expired permit within 90 days;
- an expired permit older than 90 days;
- a permit with renewal history;
- an awaiting-payment permit;
- a withdrawn permit for search and view coverage.

Tests must cover both successful and rejected renewal paths, including the fee cap and zero-fee Council Use rule.

## Documentation updates

When code and documentation disagree:

1. Identify the disagreement.
2. Decide whether it is a requirement conflict, an implementation gap, or a coding defect.
3. Update the technical document and assumptions record.
4. Update the code and tests.
5. Mention the change in `DECISIONS.md`.

Keep diagrams, endpoint examples, data fields, and status names synchronized with the technical document.

## Scope boundaries

Do not add these to Part 2 unless the requirements are formally expanded:

- payment processing or a payment screen;
- public booking functionality;
- Excel export;
- printing;
- authentication or actor identity;
- withdrawal or cancellation workflows;
- draft-status behaviour;
- production deployment infrastructure.

## Security and data handling

- Do not commit secrets, `.env` files, credentials, or production data.
- Do not expose stack traces or persistence errors in API responses.
- Validate all client-supplied dates, identifiers, and text at the API boundary.
- Keep error messages useful to officers without leaking internal implementation details.

## Working style

- Prefer the smallest implementation that satisfies the technical document.
- Reuse existing project patterns before adding abstractions.
- Add focused tests for non-trivial business rules.
- Keep commits small and meaningful. Do not squash the history.
- Review the diff before committing.
- With Eclipse null analysis enabled, prefer explicit lambdas over unbound instance method references such as `Hall::active` or `String::trim`; this avoids unchecked receiver nullness conversions.
- Keep services cohesive and small: separate query, renewal, and persistence responsibilities instead of allowing one service to become a catch-all.
- Preserve meaningful failure context when wrapping persistence errors; log the cause server-side while returning only the documented API error shape.
- Follow established Spring and Java best practices: keep controllers thin, keep business rules in services, use constructor injection, validate at API boundaries, and run the relevant tests after refactoring.
- Keep React components focused and readable: move API calls and formatting helpers out of page components, split dense UI sections into focused components, preserve explicit loading/error states, and avoid unnecessary re-render abstractions.
